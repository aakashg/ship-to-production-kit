# DECISIONS: Usage-based spend alerts

Version: v1 (headless run, 2026-11-20). No human was available, so no product question was answered by me. Every `needs you` row below carries my recommendation as a recorded assumption; the plan is written to that recommendation, and changes if you answer differently.

`needs you` rows come first.

| # | Decision | Options | Recommendation and why | Risk | Decided by |
|---|----------|---------|------------------------|------|-----------|
| 1 | Stack and existing metering. The repo is an empty template. Does the gateway already compute per-request cost, have a usage event channel, a relational DB, an authz layer, an email path? What language? | (a) Python + Postgres + existing queue, as assumed in ENG-PLAN A1 to A5. (b) Something else. (c) Parts missing, so M0 adds them. | Assume (a). Everything in ENG-PLAN paths hinges on it, and M0 verifies before any code. If cost metering does not exist, this feature grows a lot and needs re-estimating. | high | needs you |
| 2 | Does 100% block traffic? | (a) Alert only in v1. (b) Block at 100%. (c) Per-key setting, default alert only. | (a). The request was for alerts. Blocking production traffic is a different promise and a different failure mode. The counter is built so a cap can be added later (Cloudflare and LiteLLM both separate soft and hard limits; see PRD market table). Emails must say "requests are not blocked". Experiment result may change this. | high | needs you |
| 3 | Budget period and timezone. | (a) Calendar month, UTC. (b) Calendar month in org timezone. (c) Billing-cycle anchor date. | (a). Simplest, deterministic, matches Portkey's UTC reset ([source](https://portkey.ai/docs/product/observability/budget-limits)). Customers in other zones will see reset at a non-midnight local time; state it in the UI and email. Switching later migrates counters. | med | needs you |
| 4 | Source of truth for "spend". | (a) Gateway estimate from token counts and list price. (b) Provider-reported usage or invoice. (c) Hybrid with reconciliation to provider. | (a), labelled "estimated" everywhere. Provider invoices lag and differ per provider; Cloudflare's gateway also uses estimates ([docs](https://developers.cloudflare.com/ai-gateway/features/spend-limits/)). Customers may still compare to invoices and dispute 100%. | high | needs you |
| 5 | Who gets alerts. | (a) Key creator only. (b) Key owner + org admins + up to 5 extra recipients, unverified. (c) Same as (b) but extra recipients must verify by link. | (b) for v1 to match what Portkey does ([docs](https://portkey.ai/docs/product/observability/budget-limits)), with (c) as fast-follow. Recipient emails are personal data and an unverified recipient could be a stranger. | high | needs you |
| 6 | Channels and email provider. | (a) Email only v1. (b) Email + signed webhook v1. (c) Email v1, webhook v1.1. Provider: existing one vs new (SES, SendGrid, Resend...). Sender domain with SPF/DKIM. | (c). Platform customers will likely want webhooks, but each channel adds security surface (SSRF, signing). I did not verify what email capability the org has. Sender domain and deliverability setup is an external promise to customers. | med | needs you |
| 7 | Alert semantics at the edges: one request jumps several thresholds; budget raised or lowered mid-month; late events after month end; alerts after 100%. | See ENG-PLAN section 6. | Send one alert for the highest crossed threshold; budget raise re-arms only thresholds above current spend, silent for passed ones; budget lowered below spend sends one `budget_changed` alert; no alert for closed periods; one 100% alert per period and version. Chosen to minimise spam but customers will notice each behaviour. | med | needs you |
| 8 | Schema migration, public API contract and plan availability. New tables; four new endpoints under `/v1/api-keys/{id}/budget`; which plans get it. | Tables as in ENG-PLAN section 3. Endpoints as section 4. Plans: all vs paid vs enterprise (Portkey gates it to Enterprise and select Pro; LiteLLM email alerts reportedly enterprise, both unverified for current terms). | Additive migration only; endpoints as written; available on all plans for v1 (my guess, no pricing input). Migration, API and packaging all need human owners per guardrails and CODEOWNERS. | high | needs you |
| 9 | Success targets and pilot cohort. | Targets: 95% of alerts within 5 minutes, 30% adoption in 60 days, zero duplicates. Cohort: internal first, then which customers. | Use the PRD targets as placeholders; baselines are unknown. A human picks 3 to 5 pilot customers and runs the experiment on real usage logs before M3 if possible. | med | needs you |
| 10 | How spend is counted: hot path or async. | (a) Inline in request path (e.g. DB update per request). (b) Emit event, async aggregator. | (b). Zero added latency or failure modes on the hot path, and batching is possible. Cost is a few seconds of alert lag, which the 5-minute target tolerates. | low | agent: (b) async aggregator |
| 11 | Money type and dedupe keys. | Float dollars vs decimal vs integer micro-USD. Dedupe by event id vs request id vs unique constraint. | Integer micro-USD (BIGINT), integer-only threshold math (`old*100 < t*budget <= new*100`). `processed_usage_events` PK on request_id for increments; UNIQUE (key, period, threshold, budget_version) for alerts. Avoids rounding bugs and double-sends. | low | agent |
| 12 | Delivery reliability pattern. | Send inline from aggregator vs transactional outbox with worker. | Outbox row in the same transaction as the counter update; separate notifier with exponential backoff up to 24h; provider idempotency key = event id. A crash cannot lose an alert; a rare duplicate email is accepted. | low | agent |
| 13 | Observability names and privacy of content. | Metric, log and field naming; what goes in emails and logs. | Names as in ENG-PLAN section 9 (`spend_alerts_*`, `spend.*` log events with `request_id` and `trace_id`). Emails and logs show key alias and last 4 chars only, never secrets or full recipient addresses (domain plus hash in logs). Alarm routing channel is still empty in docs/OBSERVABILITY.md, so it will be filled once a human names one. | low | agent |
| 14 | Rollout mechanics. | Straight launch vs shadow mode then per-org flag with staged steps. | Shadow mode for at least a week (compute, compare to reconcile, send nothing), then `send_enabled` per org: internal, pilot, 1%, 10%, 50%, 100%. Rollback is one flag flip. Follows the repo rule to ship 1 percent first. | low | agent |
